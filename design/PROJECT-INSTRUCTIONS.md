# Pandora Spec — инструкции проекта

**Pandora Spec** (кодовое имя **SpeCMP**) — приложение для монтажа автомобильных
сигнализаций Pandora на **Android, iOS, планшетах и Desktop**, собранное на Kotlin Multiplatform +
Compose Multiplatform из единой кодовой базы. Основные пользователи — **автомеханики
30–50 лет с малочувствительными пальцами**: отсюда главное правило — **никаких мелких
элементов**, зоны касания ≥ 48 dp, крупная типографика, высокий контраст. Визуальный язык —
Material 3, сгенерированный из seed-цвета `#2C3639`; обязательны **светлая и тёмная** темы.
Все макеты — React + Babel inline JSX, использующие компоненты `Cmp*` из дизайн-системы.

## Структура проекта

```
index.html                  Точка входа: фрейм устройства + переключатель тем (Светлая/Тёмная)
                            и навигация. Монтирует components/app-kit + features/calculator.
CLAUDE.md                   Этот файл — инструкции проекта.
styles.css                  Корневой shim компилятора → @import design-system/styles.css.

design-system/              Дизайн-система Pandora Spec (источник правды по визуалу)
  styles.css                Манифест @import'ов токенов (реальная точка входа)
  tokens/                   colors.css · typography.css · spacing.css · fonts.css — переменные (--*)
  guidelines/               HTML-карточки гайдлайнов: цвета, типографика, спейсинг, бренд
  handoff/                  Спеки для разработки
  readme.md · SKILL.md      Описание системы и правила её использования

components/                 Переиспользуемые UI-примитивы Cmp* (обёртки над Material 3)
  app-kit/                  CmpText, CmpIcon, useStateLayer, PhoneFrame — каркас прототипов
  buttons/ forms/ surfaces/ navigation/ feedback/ progress/
                            Каждый компонент: .jsx (реализация) + .d.ts (типы) + .prompt.md
                            (как использовать) + *.card.html (демо-карточка группы)

features/                   Экраны продукта
  calculator/               Calculator.jsx (экран) + Calculator.html (mobile) +
                            CalculatorDesktop.html (опорное окно 800×600). README.md.
                            <feature>/shared/ — переиспользуемые части фичи (по мере роста).

res/                        Общие ресурсы
  nav.js                    Кросс-макетная навигация: window.psGo('calculator') (LINKS → файлы)
  icons/cmp-icons.js        Каталог иконок CmpIcons (для прототипов без бандла)

changelog/                  История изменений макетов (черновики-бакеты → финальные записи)
skills/                     Проектные скиллы (процедуры для агента, см. ниже)
uploads/                    Исходники: спека дизайн-системы, референсы.

_ds_bundle.js · _ds_manifest.json · _adherence.oxlintrc.json
                            Генерируются компилятором — НЕ править руками. В отличие от
                            референс-проектов лежат в КОРНЕ (требование платформы: компилятор
                            сканирует от корня и ждёт там styles.css).
```

Конвенции:
- Стандартные ссылки между макетами — через `window.psGo(key)` из `res/nav.js`, не хардкод путей.
- Цвета и размеры — только токены дизайн-системы (`--*`); темы переключаются через `data-theme`.
- Зона касания ≥ 48 dp; экран обязан корректно выглядеть в светлой и тёмной теме; на Desktop —
  продуманные состояния hover/focus.
- **Поддержка планшетов обязательна.** Каждый экран должен иметь продуманный планшетный
  лейаут (≈600–1024 dp по ширине), а не растянутый телефонный: используй пространство —
  двухколоночные/master-detail компоновки, более широкие контейнеры с разумными max-width,
  крупная типографика и зоны касания ≥ 48 dp сохраняются. Учитывай и портрет, и ландшафт.
  Где уместно — давай в макетах опорное планшетное окно наравне с mobile и Desktop.
- Глубина папок внутри `features/` фиксирована — относительные пути (`../../styles.css`,
  `../../_ds_bundle.js`, `../../components/app-kit/...`) на это рассчитывают.
- Компоненты называются с префиксом `Cmp*` (как в реальном коде); экспорт — именованный, чтобы
  попасть в бандл (`window.PandoraSpecDesignSystem_*`).

## Размеры экранов

Брейкпоинты — по **Material 3 Window Size Classes** (ширина окна в dp). Лейаут выбирается
по классу окна, а не по «телефон/планшет»:

- **Compact** — ширина `< 600 dp`. Телефоны в портрете. Одна колонка, нижняя навигация.
- **Medium** — ширина `600–839 dp`. Планшеты в портрете, малые планшеты, телефоны-ландшафт.
  Боковой navigation rail, более широкие контейнеры, возможен master-detail.
- **Expanded** — ширина `≥ 840 dp`. Планшеты-ландшафт и Desktop. Двухколоночный master-detail,
  постоянный navigation rail/drawer, контент с `max-width` и центрированием.

Опорные окна для макетов (используй именно их при превью, mobile / tablet / desktop наравне):

| Тип устройства        | Класс    | Опорное окно (dp/px) | Примечание                              |
|-----------------------|----------|----------------------|-----------------------------------------|
| Телефон (портрет)     | Compact  | `412 × 915`          | базовый Android-фрейм в `index.html`    |
| Телефон (ландшафт)    | Medium   | `915 × 412`          | проверять, что контент не ломается      |
| Планшет (портрет)     | Medium   | `800 × 1280`         | navigation rail + широкий контент       |
| Планшет (ландшафт)    | Expanded | `1280 × 800`         | master-detail, две колонки              |
| Desktop (окно)        | Expanded | `1280 × 800`         | min поддерживаемое `800 × 600`          |

Правила:
- Контент тянется не бесконечно: на Expanded задавай разумный `max-width` (≈840–1040 dp для
  основной колонки) и центрируй, чтобы строки текста и формы не растягивались на всю ширину.
- Зоны касания ≥ 48 dp и крупная типографика сохраняются на ВСЕХ классах.
- Каждый экран обязан корректно выглядеть минимум в трёх окнах: Compact, Medium-планшет и
  Expanded/Desktop — в светлой и тёмной теме.

## Ведение changelog

История изменений макетов ведётся в `changelog/` в два этапа: черновики-фрагменты по чатам →
слияние в одну финальную запись.

### 1. В каждом новом чате — свой черновик-фрагмент
Черновики копятся в бакетах-поддиректориях: стандартный `changelog/current/` или отдельный
`changelog/<слаг-фичи>/` (имена фиксированы, **без даты**). Как только в чате начинается работа
над функционалом:
- **Спроси пользователя, куда писать changelog этого чата** (по умолчанию — `current`).
- Создай в бакете **новый** файл-фрагмент `<слаг-экранов>.md` и заполняй по ходу работы.
- Один чат → один фрагмент. Структура фрагмента — как у записи (см. `changelog/README.md`).

### 2. По завершении — слияние
Когда пользователь сообщает, что работа над фичей закончена, он **явно** вызывает скилл
`skills/merge-changelog/`. Сам, без просьбы, слияние не запускай.

## Скиллы проекта

В `skills/` лежат проектные процедуры (каждая — папка с `SKILL.md` и frontmatter). Если запрос
пользователя подходит под скилл, прочитай его `SKILL.md` и следуй ему.

- **`skills/merge-changelog/`** — слияние черновиков-фрагментов changelog в одну финальную запись
  `changelog/<дата>-<экраны>.md` и удаление слитого бакета. Вызывается ЯВНО по завершении фичи.
  Триггеры: «слить / смерджить / собрать / закрыть changelog», «зафиксировать фичу».
- **`skills/import-by-changelog/`** — выравнивание локальных макетов по changelog из целиковой
  выгрузки проекта. Триггеры: «синхронизировать / подтянуть / выровнять» из свежей копии.
- **`skills/export-handoff/`** — упаковка проекта в zip (бэкап) + генерация инструкции
  `HANDOFF.md` для агента-разработчика по конкретным экранам. Триггеры: «выгрузить / забэкапить /
  передать в разработку / хендофф».
