# perf-bench: бенчмарк производительности до и после задачи

Скилл `perf-bench` меряет приложение утилитами (`adb`, `dumpsys`, Perfetto, `apkanalyzer`, Maestro) и сравнивает
замер «после» с замером «до» по строгим правилам. Модель числа не оценивает: она запускает команды и пересказывает
`report.md`. Источник скилла — `.ai/skills/perf-bench/` (`SKILL.md` — сценарий для агента, `metrics-registry.json` —
реестр метрик, `scenarios.json` и `scenarios/*.yaml` — сценарии, `scripts/` — сборщики), рабочая копия после
`.ai/generate.sh` — `.agents/skills/perf-bench/`, вывод — `.ai-perf/bench/` (вне git).

`perf-bench` меряет приложение на эмуляторе; `perf-audit` — статический аудит кода (репозитории, ViewModel,
Compose) без запуска. Они дополняют друг друга.

## Цикл в задаче

Скилл не обязателен: запускается по просьбе пользователя и в задачах, где важна производительность (старт,
списки, тяжёлые экраны, память, оптимизации). В обычных задачах его не запускают.

```
B=.agents/skills/perf-bench/scripts/bench.sh
$B doctor                                               # окружение: adb, apkanalyzer, устройство, maestro, venv perfetto
$B baseline --scope static,startup,trace,feature:auto   # до правок кода → baselines/<sha>.json
… правки, сборка, spotless, detekt …
$B run      --scope static,startup,trace,feature:auto   # сравнение с базой → runs/<дата>-<sha7>-run/report.{md,html}
```

База ищется по `git merge-base HEAD develop`; если её нет — берётся последняя с предупреждением. `--platform
android|ios|both` (по умолчанию `android`), `--no-build` — только если меряется уже установленная сборка.

Креды QA-аккаунта для флоу: `.agents/skills/perf-bench/credentials.properties` (шаблон рядом), иначе — креды
`ui-test` (`.agents/skills/ui-test/credentials.properties`).

| `--scope` | Что меряет | Когда |
|---|---|---|
| `static` | размер APK и разбивка, dex-методы по модулям, строки Kotlin по модулям, detekt, unit-тесты | всегда |
| `startup` | холодный старт N раз: TTID (`am start -W`), TTFC (появление главной), кадры, кадры за окно простоя (0 — экран статичен; десятки — зацикленная анимация), PSS и heap, число экземпляров Activity (норма 1), CPU, GC, ошибки, крэши, ANR | всегда |
| `trace` | один старт под Perfetto: `bindApplication`, `activityStart`, первые кадры, состояния главного потока, самые долгие слайсы | всегда (нужен venv: `python3 -m venv .ai-perf/bench/.venv && .ai-perf/bench/.venv/bin/pip install perfetto`) |
| `compose` | сборка с `scripts/compose-reports.init.gradle` (отчёты в `<модуль>/build/compose-reports/`): доля skippable composable, unstable-классы по модулям | правки UI в `feature/*`, `core/ui`, `composeApp` |
| `feature:auto` | Maestro-сценарии по изменённым модулям (`login`, `main-menu`, `vehicles`): K повторов в одном процессе — кадры, кадры в простое после флоу, память после GC и её рост (утечка), экземпляры Activity, CPU, ошибки | при `baseline` / `run` по задаче; `feature:<name>` / `feature:all` — вручную |
| `stability` | monkey с фиксированным seed (крэши, ANR), старт без сети и восстановление | правки `core/*`, `composeApp` |

Модуль для `feature:auto` — путь до `src/` изменённого файла (`feature/device/firmware`); модуль сценария покрывает
вложенные (`feature/device` → `feature/device/*`).

## Как читается вердикт

- Δ = текущее − база; «лучше» задано у каждой метрики (меньше — для времени, памяти, размера; больше — для тестов).
- Регресс засчитывается только при |Δ| > шум = 2 × MAD (разброс замеров базы или текущего прогона).
- ⚠️ / ❌ — когда |Δ| не меньше порога по абсолюту **и** по проценту из реестра. Крэши, ANR, упавшие тесты и
  повторы сценариев — ❌ при любом значении больше нуля, без базы.
- Вердикт прогона — худший статус. ❌ — задача не завершена, пока регресс не объяснён пользователю; «Заметки
  сборщика» (нет отчётов detekt, контент не появился, флоу упал) — ограничения замера, не регресс.
- Определение каждой метрики (команда, формула, пороги) — в реестре и в `report.html` по значку ⓘ;
  `bench.sh metrics` печатает реестр таблицей.

## Сценарии

| Сценарий | Флоу | Что делает |
|---|---|---|
| предусловие старта | `scenarios/ensure-main.yaml` | открыть приложение; на экране входа — войти QA-аккаунтом; дождаться главной |
| `login` | `scenarios/login.yaml` | очистка данных, холодный старт, вход → главная (`reset_each`) |
| `main-menu` | `scenarios/main-menu.yaml` | скролл главной, боковое меню → «Настройки» → назад (только Android) |
| `vehicles` | `scenarios/vehicles.yaml` | «Автомобили» → «Сигнализация» → скролл марок → модели Audi → назад (только Android) |

Шаги входа — `scenarios/login-steps.yaml`. Тексты — en|ru (`"Quick install|Быстрый монтаж"`): язык приложения на
стенде любой. Флоу должен заканчиваться на том же экране, с которого начал (главная, список в начале), — иначе
следующий повтор начнётся с другого экрана. Новый сценарий: флоу в `scenarios/`, запись в `scenarios.json →
features` (модули, повторы, платформы), прогнать `bench.sh baseline --scope feature:<name> --no-build` дважды.

## Ограничения

- Стенд — эмулятор: сравнимы только дельты на одном стенде; отчёт печатает AVD, API, CPU и масштаб анимаций.
- Экраны с BLE/USB-устройством (прошивки, конфигуратор, расширенный монтаж, подключение) на эмуляторе не мерятся.
- Debug-сборка без R8 и JIT-профилей; абсолютные значения выше релизных.
- Нет сетевых метрик (лог сети SDK выключен) и TTFD (приложение не вызывает `reportFullyDrawn`).
- Композиционный трейс главной (`trace`, метрики «Главная: …») пропускается: нужен
  `androidx.compose.runtime:runtime-tracing` в debug-сборке, а `AppActivity` — `singleTask`, поэтому способ
  «новый экземпляр Activity» не воспроизводит начальную композицию.
- Флоу идут по текстам экранов — смена текста ломает флоу (`flow_failed`), это не регресс производительности.
- Длительность флоу в основном — ожидания Maestro «экран стабилен»; метрика справочная.
- Пороги реестра откалиброваны в исходном проекте на `Pixel_10_Pro` (API 36); при смене стенда калибровать заново.
