# perf-bench

Числа считают скрипты, модель их **не оценивает и не пересчитывает** — только запускает команды и
пересказывает `report.md`. Все пути — от корня репозитория. Скрипт: `B=.agents/skills/perf-bench/scripts/bench.sh`.
Вывод: `.ai-perf/bench/` (вне git). Определения метрик и пороги — `.agents/skills/perf-bench/metrics-registry.json`
(`$B metrics` печатает их таблицей). Процесс и ограничения — `docs/test/perf-bench.md`.

## Когда и что запускать

| Момент | Команда | Зачем |
|---|---|---|
| Задача, где важна производительность: начало, код ещё не тронут | `$B baseline` | замер «до»: `baselines/<sha>.json` |
| Та же задача завершена (сборка и качество прошли) | `$B run` | замер «после» и сравнение с базой → вердикт |
| Пользователь попросил `/perf-bench` | по его словам: `baseline`, `run`, `compare`, `report`, `list` | |

Опции обеих команд: `--platform android|ios|both` (по умолчанию `android`), `--runs N` (замеров старта, по
умолчанию 5), `--label <текст>`, `--no-build` (меряется уже установленная сборка — только если пользователь прямо об
этом попросил), `--apk <путь>`, `--scope <список>` — состав прогона.

## Состав прогона (`--scope`)

| Часть | Что меряет | Когда включать |
|---|---|---|
| `static` | APK, dex, строки кода, detekt, unit-тесты | всегда (по умолчанию) |
| `startup` | холодный старт: TTID, TTFC, кадры, память, CPU, ошибки | всегда (по умолчанию) |
| `trace` | Perfetto-трейс одного старта: bindApplication, activityStart, первые кадры, состояния главного потока, самые долгие слайсы | всегда (по умолчанию); нужен venv: `python3 -m venv .ai-perf/bench/.venv && .ai-perf/bench/.venv/bin/pip install perfetto` (doctor подскажет), без него пропускается с заметкой |
| `compose` | сборка с init-скриптом отчётов Compose-компилятора: доля skippable composable и число unstable-классов по модулям | задача трогала `feature/*` (UI), `core/ui` или `composeApp`; +2 мин к сборке |
| `feature:auto` | Maestro-сценарии фич, чьи модули изменены относительно `develop` (карта — `scenarios.json → features.*.modules`) | при `baseline` и `run` по задаче |
| `feature:<name>` / `feature:all` | конкретный сценарий / все (`login`, `main-menu`, `vehicles`) | по просьбе пользователя |
| `stability` | monkey с фиксированным seed (крэши, ANR), старт без сети и восстановление | задача трогала `core/*`, `composeApp` или сеть/навигацию |

Команда по задаче: `$B baseline --scope static,startup,trace,feature:auto` в начале и
`$B run --scope static,startup,trace,feature:auto` в конце; `,compose` и `,stability` добавляются по правилам из
таблицы, одинаково в обе команды — иначе у метрик не будет базы. `feature:auto` печатает «сценариев для прогона
нет», если изменённые модули не входят ни в один сценарий — это не ошибка; сообщить пользователю, что фичу можно
покрыть новым флоу в `scenarios/` (флоу пишет пользователь или отдельная задача, в этом скиле код и флоу не
создаются). Экраны, которым нужно BLE/USB-устройство (прошивки, конфигуратор, расширенный монтаж), на эмуляторе
не мерятся.

Сценарий фичи прогоняется K раз в одном процессе (`repeats`): кадры, память после принудительного GC, рост памяти
между первым и последним повтором (утечка), CPU, ошибки. Сценарии и предусловие старта входят QA-аккаунтом:
креды — `credentials.properties` рядом со скилом, а если его нет — `.agents/skills/ui-test/credentials.properties`.

## Шаги

1. **Окружение.** `$B doctor [--platform …]`. Любой ❌ — показать пользователю строку с командой из вывода и
   остановиться; iOS требует запущенного симулятора и открытого Simulator.app.
2. **Замер.** `$B baseline …` или `$B run …`. Команда сама собирает APK (и iOS-приложение при `--platform ios|both`),
   устанавливает, прогоняет предусловие (`scenarios/ensure-main.yaml`: вход и главная), делает прогрев и N холодных
   стартов, снимает дампы и пишет `results.json`, `report.md`, `report.html`. Длительность: Android ≈ 3–4 мин плюс
   сборка; iOS дольше из-за xcodebuild. Прогон упал (`ERROR:`) — показать строку ошибки пользователю; код
   приложения в этом скиле не править.
3. **Результат.** Прочитать `report.md` (путь печатается в конце как `REPORT:`) и передать пользователю:
   - строку «Вердикт», базу и стенд;
   - список «Причины» дословно (метрика, база → текущее, Δ, порог);
   - «Заметки сборщика» — это ограничения замера (нет отчётов detekt, не COLD-запуск, контент не появился), не регресс;
   - путь к `report.html` для разбора глазами.
   Если у задачи есть файл задачи (`.claude/tasks/…`) — вписать туда вердикт, причины и путь к прогону.
4. **Нет базы.** `run` печатает `⚠️ базы нет` и отчёт без сравнения. Сказать пользователю, что сравнения нет, и
   предложить снять базу на develop: `git stash`/checkout базового коммита → `$B baseline` → вернуться → `$B run`.
   Самому переключать ветки без разрешения нельзя.

## Как читать вердикт (правило из реестра, модель его не меняет)

- Δ = текущее − база. Регресс — ухудшение по направлению метрики («меньше — лучше» для времени, памяти,
  размера; «больше — лучше» для числа тестов).
- Регресс засчитывается только если |Δ| больше шума: 2 × MAD (разброс замеров) базы или текущего прогона.
- ⚠️ warn / ❌ fail — когда |Δ| не меньше порога по абсолюту **и** по проценту (оба записаны в реестре).
  Крэши, ANR, упавшие тесты — ❌ при любом значении больше 0 независимо от базы.
- ✅ ok — изменение в пределах шума или ниже warn; 🟢 — улучшение; ℹ️ — справочная метрика без вердикта.
- Вердикт прогона — худший статус среди метрик. Числа в отчёте не округлять в пересказе и не «объяснять»
  регресс догадками: причины ищут программист или отдельный разбор по `raw/` и `report.html`.

## Ограничения

- Стенд — эмулятор: абсолютные значения выше, чем на устройстве, сравнимы только дельты на одном стенде.
  Отчёт печатает стенд (AVD, API, CPU, масштаб анимаций); разные стенды сравнивать нельзя.
- Debug-сборка `:androidApp:assembleDebug`: без R8 и JIT-профилей. Для отчёта это норма — меняется только дельта.
- Кадров (`gfxinfo`) на iOS нет; сетевых метрик нет ни на одной платформе (лог сети SDK выключен).
- TTFC ждёт `scenarios.json → startup.content_tag` — текст главной («Quick install|Быстрый монтаж»): testTag на
  главной нет. Экран без него (вход, обновление приложения) даёт «нет данных» в этой строке — остальные метрики
  остаются. TTFD (`reportFullyDrawn`) приложение пока не сообщает — строка без данных.
- Композиционный трейс главной (метрики «Главная: …» в `trace`) пропускается: в debug-сборке нет
  `androidx.compose.runtime:runtime-tracing`, а `AppActivity` — `singleTask`.
- Флоу фич используют тексты экранов (en|ru) и testTag там, где они есть: смена текста ломает флоу — `flow_failed`
  в отчёте и лог `raw/android/feature-<name>/repeat-*/maestro.log`. Это не регресс производительности; сообщить
  пользователю, что флоу нужно обновить.
- Упавший повтор в агрегат не входит; если упали все — у сценария только `flow_failed`.
