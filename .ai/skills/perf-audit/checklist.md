# Чек-лист аудита производительности

Правила проекта (`docs/patterns.md`, `docs/compose-best-prac.md`) первичны: рекомендация, которая им
противоречит, — не находка. Типовые ловушки: «обернуть метод репозитория в `withContext`» (запрещено —
диспетчер переключает вызывающий, обычно VM), «запустить загрузку из `LaunchedEffect`» (запрещено —
триггер это подписка на `state`), «добавить в репозиторий поколения/флаги/volatile» (репозиторий тонкий,
решения о повторах и сбросах — во VM).

## Как оценивать

Находка = **стоимость × частота на горячем пути**. Без частоты нет приоритета.

| Уровень | Когда |
|---|---|
| 🔴 высокий | Горячий путь: каждый кадр скролла/анимации, каждый символ ввода, каждое BLE/SDK-событие, поллинг; блокировка main > ~16 мс; утечка памяти/подписки; сетевой запрос, повторяющийся без нужды на каждом входе/событии |
| 🟡 средний | Лишняя работа на событиях средней частоты (вход на экран, клик, смена фильтра); рекомпозиция крупного поддерева без визуальных изменений |
| 🟢 низкий | Микрооптимизация вне горячего пути. Записывается, но к правке рекомендуется только если тривиальна |

Частоты горячих путей в этом проекте: события устройства по BLE (`feature/device/*`, поток статуса и
телеметрии), поиск/фильтры каталога (`feature/vehicle*`), ленты и ввод чата (`feature/support-chat`),
поллинг (непрочитанные и т. п.), скролл любых `Lazy*`-списков.

Каждая находка обязана содержать: `файл:строка`, какой путь горячий и как часто срабатывает (из кода, не
«возможно»), конкретную правку в духе правил проекта. Нет доказательства частоты/стоимости — не находка,
а «вопрос» в отдельном разделе отчёта.

## R — Репозитории (`data/repository`, `core/*`)

- **R1. Повторная загрузка неизменных данных.** Справочник/каталог/конфиг грузится с сети или SDK на
  каждый вход на экран или каждый вызов. Правка: простой кэш в `single`-репозитории (одно поле
  `MutableStateFlow<T?>`/значение под `Mutex`), сброс в `release()` (`AuthCloseable`), если данные
  аккаунта. Не городить TTL/поколения без требования.
- **R2. N+1 и последовательные независимые вызовы.** Запрос в цикле по элементам; два независимых
  вызова подряд. Правка: batch-метод SDK/API, иначе `coroutineScope { awaitAll(async {…}) }` — только
  если SDK потокобезопасен для параллельных вызовов (проверить, BLE-сессия обычно — нет).
- **R3. Блокирующий код в `suspend`.** `runBlocking`, синхронный файловый/сокетный I/O, `Thread.sleep`,
  тяжёлый парсинг больших ответов. Находка ставится на **место вызова** (VM: `withContext(dispatchers.io /
  default)`), не в репозиторий — если только у репозитория нет собственной фоновой логики.
- **R4. Тяжёлый маппинг.** Маппинг больших коллекций цепочкой `map/filter/sortedBy/groupBy` с
  промежуточными копиями; повторная сортировка уже отсортированного; regex/парсинг дат в цикле без
  предкомпиляции. Значимо только для больших N или горячего пути.
- **R5. Дублирование холодных потоков.** Холодный `Flow` (поллинг, `callbackFlow` над SDK) собирается
  несколькими подписчиками — каждый запускает свой цикл/регистрацию. Правка: один коллектор на уровне
  владельца (VM `stateIn`, app-scoped `shareIn` только при реальной общей подписке).
- **R6. Лишние эмиты.** Поллинг/событийный поток отдаёт одинаковые значения — downstream (VM `combine`,
  рекомпозиция) работает впустую. Правка: `distinctUntilChanged()` на источнике/в VM.
- **R7. Утечки подписок.** `callbackFlow` без `awaitClose { unregister }`, листенеры SDK без снятия,
  `CoroutineScope` в singleton без отмены, данные прошлого аккаунта не чистятся в `release()`.
- **R8. Большие данные целиком.** `Response<ByteArray>`/полный список там, где нужна пагинация или
  потоковая запись (риск OOM на слабом Android).
- **R9. Нет таймаута.** Ожидание ответа устройства/сети без `withTimeout` — экран висит в загрузке.

## V — ViewModel (`ui/presentation/**/*ViewModel.kt`)

- **V1. Работа на Main.** Маппинг/фильтр/сортировка/поиск по большим спискам внутри `update {}`,
  `combine {}` или интента без `flowOn(dispatchers.default)` / `withContext`. Вызов блокирующего
  репозитория без `withContext(dispatchers.io)`.
- **V2. Пересчёт всего на любой эмит.** `combine(a, b, c) { тяжёлая сборка }`, где тяжёлая часть зависит
  только от `a`, а `c` эмитит часто. Правка: вынести дорогое в отдельный `a.map {…}` (кэшируется по
  эмиту `a`), `distinctUntilChanged` на частых источниках.
- **V3. Монолитный state с горячими полями.** Прогресс/таймер/телеметрия/черновик ввода лежат в одном
  `XxxState` со списком → каждое обновление пересобирает state и рекомпозирует экран. Правка: отдельный
  `StateFlow` для горячего поля или чтение его только в листовом composable (см. C3); черновик ввода —
  локально в composable (`compose-best-prac.md` §9).
- **V4. Ввод без debounce / без отмены.** Поиск/фильтр шлёт запрос или пересчёт на каждый символ;
  новая загрузка не отменяет предыдущую. Правка: `MutableStateFlow(query).debounce(…)
  .flatMapLatest {…}` в цепочке state, не ручные `Job`-поля.
- **V5. Неверная `SharingStarted`.** `Eagerly` для тяжёлого источника; `Lazily` для поллинга (не
  останавливается, батарея); `WhileSubscribed` для дорогой init-загрузки, которая перезапускается после
  каждого возврата на экран (> stopTimeout) без нужды. Сверять с таблицей в `docs/patterns.md`.
- **V6. Тяжёлый `onStart` на цепочке state.** Долгая suspend-работа в `onStart` блокирует первый эмит —
  экран без начального состояния.
- **V7. Частые UI-события поштучно.** Видимость элементов, скролл → вызов VM/сети на каждое событие.
  Правка: пачка из UI + батч во VM (`docs/patterns.md`, «Корректность state»).
- **V8. Пересборка коллекций на каждое мелкое обновление** горячего потока (`list.map { if (id==…) copy }`
  на каждое BLE-событие при больших N). Правка: map по id, `persistentListOf`/`PersistentMap`
  (`kotlinx-collections-immutable` уже в проекте).
- **V9. Тяжёлые объекты в state.** `ByteArray`/битмапы/большие строки — `equals` при каждом
  `update`/`stateIn` и удержание памяти. Правка: держать ссылку/id, данные — вне state.
- **V10. Работа, переживающая экран.** Ручные циклы `while` с `delay` во VM, `Job`-поля, подписки,
  не завязанные на `viewModelScope`/подписку на state.

## C — Compose (`ui/presentation/**`, `core/ui`)

Сначала — выжимка отчётов компилятора (`compose-reports.sh`). С Strong Skipping нестабильный параметр
не отключает skip, но сравнивается **по ссылке**: проблема реальна, только если на каждый эмит state
приходит **новый экземпляр** с теми же данными (маппинг в composable или во VM на каждый эмит).

- **C1. Unstable-параметры на горячем пути.** Domain-тип / `List` / `IntRange` параметром composable,
  который рекомпозируется часто (элемент списка, строка в ленте), и экземпляр пересоздаётся при каждом
  эмите. Правка — **кодом**: сохранение идентичности экземпляров во VM (не пересоздавать неизменённое),
  `@Immutable` presentation-модель (не аннотация в domain), `ImmutableList`. `config/compose/stability.conf` —
  **крайняя мера**: только для неизменяемого типа из модуля без Compose, когда кодом не решается, с обоснованием
  в находке (условия — `docs/compose-best-prac.md` §3.5).
- **C2. Вычисления в теле composable.** `sortedBy/filter/groupBy/format/Regex/парсинг дат` без
  `remember(keys)`; `remember` с ключом-всем-state (пересчёт на любое изменение). Правка: перенести в
  state VM (инварианты держит state) или `remember` с узкими ключами.
- **C3. Высокое чтение быстро меняющегося state.** Скролл-оффсет, анимируемое значение, прогресс читаются
  в родителе → рекомпозиция всего поддерева каждый кадр. Правка: лямбда-модификаторы
  (`offset {}`, `graphicsLayer {}`, `drawBehind {}`), `derivedStateOf`, передача `() -> T`/`State<T>`.
- **C4. Списки.** `Lazy*` без `key` (или нестабильный ключ — индекс при вставках), без `contentType`
  для разнотипных элементов; `Column(verticalScroll)` + `forEach` для длинного/растущего списка;
  `BoxWithConstraints`/`SubcomposeLayout` в элементе списка; редко и часто меняющиеся данные в одном
  ключе `remember`.
- **C5. Аллокации на каждую рекомпозицию.** `listOf(...)`, `TextStyle(...)`, `Brush`, `Shape`,
  форматтеры, создаваемые в теле горячего composable без `remember`/константы.
- **C6. Сбор потоков.** `Flow` параметром дочернего composable; несколько `collectAsState` одного
  источника; в Android-коде — не lifecycle-aware сбор.
- **C7. Изображения.** Декодирование больших картинок без размера/даунсэмплинга в списках; загрузка
  мимо `LocalCmpImageLoader` (нет кэша); `painterResource` больших битмапов в элементах списка.
- **C8. Анимации и отрисовка.** `rememberInfiniteTransition`, живущая вне экрана/за диалогом; геометрия
  в `Canvas {}` без `drawWithCache`; `animate*AsState`, прочитанный в корне экрана.
- **C9. Ввод текста через state VM.** Каждый символ → `_state.update` → рекомпозиция экрана со списком
  (см. V3).
- **C10. Эффекты.** `LaunchedEffect` с ключами, меняющимися на каждый эмит (перезапуск подписки,
  `snapshotFlow` с аллокацией списка на кадр) — см. `compose-best-prac.md` §9.
