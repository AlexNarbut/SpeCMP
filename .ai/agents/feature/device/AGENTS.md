# feature/device

- Подключение к блоку и работа с ним: `selection(-ui)` — поиск и выбор (BLE + USB), `interaction(-ui)` — сессия устройства и обёртка flow (экраны «Подключение», «Потеря связи», слот экрана загрузчика), `firmware(-ui)` — проверка и обновление прошивок.
- `DeviceSession` (`interaction/domain/session`) — единственный держатель состояния подключённого блока (app-scoped, свой скоуп). На каждом `READY` определяет режим блока (`detectMode`): `Ready` / `BluetoothBoot` / `FirmwareBoot`; обрыв — `Disconnected`.
- BLE: SDK сам не переподключается (`autoConnect = false`) — переподключает `DeviceSession.reconnectWhileBle` (пауза 1 с + `reconnect()`; нативная попытка `connectGatt` без блока длится ~10 с). После `close()` транспорта нет — попыток тоже нет. USB переподключает SDK.
- Экран потери связи: после первого `READY` в BLE-сессии потеря связи остаётся `Disconnected` на всё переподключение — `CONNECTING` от попыток и чтение режима не подменяют её на `Connecting` (флаг `wasReady`, сбрасывается `attach()`). «Подключение к блоку…» — только при первом подключении.
- Диагностика: `DeviceSession.logStage` пишет `logger.i` с временем от `attach()` (`+Nms link=… / state=… / reconnect #N start|end / detectMode / read attempt`), `ScanDeviceViewModel.connectBle` — старт/результат попыток. Замеры подключения и переподключения брать из этих логов (`adb logcat --pid`, теги `DeviceSession`, `ScanDeviceViewModel`), а не секундомером.
- Тайминги (Android, BLE): подключение ≈ 3 с (скан внутри SDK `connect` ≈ 0.2 с, пауза SDK перед поиском сервисов 1.5 с) + `detectMode` ≈ 2 с; возврат после BT off/on ≈ 4.5–5 с от включения адаптера.
- `testTag` для ui-test: `device_item_<id>` (строка устройства), `device_status_exit` («Выйти» на «Подключение»), `device_status_disconnect` («Отключиться» на потере связи), `advanced_mount_firmware_check` (плитка «Проверка прошивок» в `feature/advanced-mount`), прошивка — см. раздел «Прошивка». На Android теги видны снаружи как `resource-id` благодаря `testTagsAsResourceId` в `androidApp/AppActivity`.
- Известные ограничения SDK (bluetooth-common): после `GATT status=133` повтор был медленным, а параллельные записи давали `prior command is not finished` — исправлено в SDK 2.0.97 (выход из ожидания `READY` по `DISCONNECTED`; `writeMutex` на записи). Пауза 1.5 с перед `discoverServices` оставлена.

## Прошивка (`firmware`, `firmware-ui`)

- `firmware` (domain + data + DI): `FirmwareRepository` (модули блока, последняя версия, страницы архива), `FirmwareUpdateRepository` (`Flow<FirmwareUpdateProgress>`: `Preparing → Sending(%) → Verifying → Applying → Finished|Failed`), `FirmwareVersionNumber` (версии сравниваются **числами**: `3.10` новее `3.9`), `FirmwareBootRequester` (канал и модуль, выбранные на экране проверки, переживают перезагрузку блока), `FirmwareArchivePicker` (результат экрана архива), `ServicePinCooldown`. Модуль поддерживает обновление, когда SDK говорит `isBootSupported(транспорт)` **и** известна команда входа в загрузчик (`ALARM_MAIN`, часы, GPS, BMW, брелок — «основная»; `BLUETOOTH_MODULE` — «BLE-модуль»); остальные типы — «Не поддерживается».
- `firmware-ui`: `FirmwareCheckScreen` (слот `firmwareCheck` в `AdvancedMountNavGraph`, раздел «Проверка прошивок») — экран проверки версий; `FirmwareBootGraph` (слот `bootContent` в `DeviceInteractionHost`): `FirmwareUpdateScreen` → `FirmwareArchiveScreen`. `composeApp` подключает оба слота и Koin-модули `deviceFirmwareModule` / `deviceFirmwareUiModule`.
- Путь: проверка → диалог подтверждения → `DeviceSession.expectReboot(ToBoot)` + `setBootMode(target)` → блок перезагружается → сессия определяет режим (`FirmwareBoot` / `BluetoothBoot`) → хост показывает `bootContent` → источник (сервер или архив) → подтверждение версии → процесс → успех → `acknowledgeReboot()` → блок возвращается в рабочий режим → хост снова показывает рабочий flow (монтаж стартует заново).
- **Ожидаемая перезагрузка** (`DeviceSession.reboot: DeviceReboot?`): `ToBoot` снимается, когда блок вернулся в загрузчике (или `cancelReboot`, тайм-аут 60 с, `attach`/`close`); `ToMain` ставится на стадии `Applying` и держится, пока блок не в рабочем режиме **и** пользователь не подтвердил результат (тайм-аут — только до возврата блока). Благодаря ему намеренный обрыв связи не выглядит потерей связи.
- Хост (`DeviceInteractionState.showBootContent`): слот показывается, если блок в загрузчике, ждём вход в загрузчик/возврат после прошивки, либо связь пропала, пока блок был в загрузчике (`wasBoot`). Пока слот на экране, оверлеи «Потеря связи»/«Подключение» не рисуются — обрыв при передаче показывает сам экран обновления (`Lost`).
- Экран обновления: фазы `Entering` / `Finishing` / `Lost` выводятся из связи и `reboot`, а не пишутся вручную. `Apply` + блок вернулся без результата SDK → `Success`; блок после применения снова в загрузчике → `Error(ApplyingError)`; обрыв на `Prepare…Verify` → после возврата блока снова выбор источника. «Назад» заблокирован (замок) на процессе, на выборе — диалог выхода (блок остаётся в загрузчике).
- **PIN программирования — только BLE** (на USB SDK пропускает режим программирования). Обе команды входа в загрузчик идут через него: SDK сам пробует сохранённый PIN или `1111` (молчаливая первая попытка); неверный → `BootModeResult.WrongPin` → диалог PIN. После неверного PIN блок **15 с не принимает ввод** (SDK не отличает это от неверного PIN и счётчика попыток не отдаёт): блокировку считает приложение (`ServicePinCooldown`), пока она идёт — в блок ничего не шлём. `DeviceSession.setBootMode` повторяет команду через паузу **только после `Entered`** (повтор с неверным PIN продлил бы блокировку). PIN нигде не хранится в state/логах (`ServicePin.toString()` скрыт).
- `testTag` для ui-test: `firmware_channel_<release|beta|alpha>`, `firmware_module_update_<id>`, `firmware_module_refresh_<id>`, `firmware_enter_confirm`, `firmware_pin_input|submit|cancel|locked`, `firmware_source_download`, `firmware_source_archive`, `firmware_update_confirm|cancel`, `firmware_progress`, `firmware_result_ok`, `firmware_error_retry|support`, `firmware_lost_reconnect|disconnect`, `firmware_exit_dialog_confirm`, `firmware_archive_item_<версия>`, `firmware_archive_select_<версия>`, `firmware_archive_install`, `firmware_archive_rollback_confirm`, `firmware_archive_refresh`.
- Галереи состояний (PNG в `build/state-gallery/...`): `./gradlew :feature:device:firmware-ui:jvmTest --tests '*Gallery*'` — проверка, обновление (все фазы), архив.
- **Не проверено на железе** (на момент написания): порядок событий SDK при `APPLYING` / `FINISHED_SUCCESS` / обрыве; время возврата блока после перезагрузки; 15 с блокировки PIN и ответ блока в её время (по словам пользователя — «неверный PIN»); формат версий сервера и признак конца страниц архива (конец — страница без новых версий).
