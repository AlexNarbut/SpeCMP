# feature/support-chat

- Обособленная фича экрана **«Техподдержка»**: доменные модели, `SupportChatRepository`, `SupportChatOutbox`, SDK-маппинг, ViewModel и UI находятся внутри модуля. Точка входа — `SupportChatEntry` (`presentation/navigation`): composable без собственного nav3-графа, размещается как entry `SupportChatRoute` в `MainNavGraph` (`composeApp/navigation/AppNavigation.kt`). Входы в чат — карточки `Requests` и `TechSupportChat` главного экрана; переход выполняет `composeApp`.
- **Лента — `SupportChatTimeline` (`domain/timeline`)**: неизменяемое значение с инвариантами — порядок по возрастанию `time`, уникальность серверных сообщений по `serverId` независимо от автора (повторная доставка заменяет, иначе дубликат ключа `LazyColumn` → краш), FIFO-сопоставление серверного эха с оптимистичным сообщением (сначала по содержимому, затем по форме — **только вложения**: сервер может переименовать файл; текст подтверждается только тем же текстом, иначе чужой мой текст из окна 2 мин «подтвердил» бы ожидающий и тот потерялся бы, не уйдя на сервер), атомарный `tryTransition` статуса. VM меняет ленту только внутри `reduce {}` и сама инварианты не держит. Время в domain — `Instant`; в местное время (метка `HH:mm`, группировка по датам) переводит UI (`buildListItems`).
- **Соединение — `SupportChatConnection` (`Connecting / Online / Offline`)**. Ввод (текст и вложения) доступен **только в `Online`** (= SDK `Ready`): офлайн-отправка запрещена продуктово. `onSend` вне `Online` игнорируется и в VM. Статус соединения — компактная плашка **поверх ленты** (`SupportChatConnectionStatus`, не сдвигает сообщения) без действий: `SupportChatScreenState.connectionBanner` = `Connecting` («Подключение…», только первое подключение), `Reconnecting` («Нет соединения · переподключаемся…» — и для `Reconnecting`, и для `WaitingForNetwork` SDK, без мигания между ними; держит флаг `hasConnectionIssue`, сброс на `Ready`) или `AuthFailed` (без спиннера; SDK подключится сам после повторного входа). Плашка появляется, только если проблема держится дольше 1,5 с, скрывается сразу.
- **Почему сокет рвётся при открытом пикере**: Android 15+ отключает сеть процессу без видимой Activity (`dumpsys netpolicy` → `blocked=APP_BACKGROUND`) примерно через 5 с. Полноэкранный DocumentsUI уводит экран в `onStop` — обрыв; Photo Picker — нижняя шторка, сокет живёт. SDK узнаёт о блокировке через монитор сети (`core/network` `NetworkMonitor` → `CommonConfigurator.networkMonitor`, см. `core/specialist`) и ждёт сеть (`WaitingForNetwork`) вместо попыток; по возврату — переподключается сам. Без монитора блокировка не детектируется.
- **Сессия — `repository.session(): Flow<Response<SupportChatEvent>>`** (SDK 1.2.0): соединением владеет SDK (`ChatConnection`: одно соединение на процесс, заявки, `Ready` = подписка комнаты подтверждена, переподключение с backoff, ожидание сети, `AuthFailed`, логаут гасит заявки). Пока поток собирается, держится заявка (`chatSessionFlowUseCase`); отмена сбора её отпускает. Репозиторий тонкий: `Connecting` → профиль (`AccountRepository`, один раз; ошибка → `Response.Error(SupportChatUnavailableException)` и конец потока; ошибки внутри потоков SDK — только лог) → события сокета (`getChatEventsFlowUseCase`, маппинг «моё/чужое» по профилю) + `Connection(state)` из SDK (`Idle`/`Connecting` → `Connecting`, `Ready`, `Reconnecting`, `WaitingForNetwork`, `AuthFailed`). Поток сам не завершается (кроме этой ошибки). `openChat`/`closeChat`/`setChatType` для чата не используются (тип по умолчанию `Default`).
- **VM** (`BaseViewModel<SupportChatScreenState, SupportChatEffect>`): в `onStart()` восстанавливает очередь, затем собирает `session()` через `launchReplacing("session")` — всю жизнь VM, не только пока экран подписан на state (поток репозитория — на io, обработка — на main); уход с экрана (отмена `viewModelScope`) отпускает соединение. Чистые переходы state — `SupportChatTransitions.kt`; служебное (`isSessionActive`, `isLoadingHistory`, учёт прочтений `SupportChatReadIds`) — поля state. Своего цикла переподключения, backoff и реакции на `ON_START`/`ON_STOP` нет — это делает SDK; в фоне заявка держится. `Ready` → `Online`, перечитать самую новую страницу истории, затем отправить очередь; уход из `Ready` → `Offline` + `requeueUnconfirmed`. `Response.Error` сессии → полноэкранная ошибка (`withSessionUnavailable`), «Повторить» перезапускает сбор сессии.
- **История — `loadHistoryPage(cursor)`** (SDK `loadChatMessagesUseCase`, HTTP, от соединения не зависит): `cursor = null` — самая новая страница, ответ — сообщения и `nextCursor` (`null` — истории больше нет). Курсор — непрозрачный (`SupportChatHistoryCursor`, внутри номер страницы SDK), размер страницы постоянный. Одна загрузка за раз (`launchReplacing("history")`, флаг `isLoadingHistory` в state). На каждом `Ready` VM перечитывает первую страницу (перезапуская текущую загрузку); повторная первая страница пагинацию не сбрасывает — курсор-номер страницы от новых сообщений сдвигается только к дублям, их снимает дедупликация `SupportChatTimeline`. Ошибка: есть лента — тост и `isHistoryPagingFailed`, нет — полноэкранная ошибка. Очередь неотправленных уходит после первой страницы (успешной или нет).
- `SpecialistSupportChatRepository` — Koin-синглтон без полей состояния, не `AuthCloseable`: на логауте соединение и заявки гасит сам SDK, сбрасывать нечего. Сбой связи (в т.ч. SDK `NetworkNotConnectedError` — команда вне `Ready`) приходит из общего `toResponse()` как `AppException(ApiError.NoConnection)`: VM кладёт такое сообщение в очередь (`Pending`), а не в `Failed`.
- SDK — через `data/datasource/SupportChatDataSource` (`SpecialistSupportChatDataSource` — только делегирование в `ChatInteractor`); тест — `SpecialistSupportChatRepositoryTest` (фейки источника и `AccountRepository`).
- **Отправка**: каждое вложение и текст — отдельные сообщения (контент эксклюзивен, SDK не поддерживает подпись к вложению). Тип вложения задаёт источник выбора (`onImagePicked` / `onDocumentPicked`), а не содержимое. Все отправки (новые, ретраи, очередь) идут строго по одной под `executeWithProceedLock(needSkipAnother = false)`. Ретрай — только атомарным переходом `Failed → Sending` (`tryTransition`): двойной тап или action снекбара параллельно с тапом не отправит дубль. Ошибка при живом соединении → `Failed` + `MessageSendFailed(canRetry)`; ошибка из-за обрыва (соединение уже не `Online`) → `Pending`. Сообщение без живого локального файла повторить нельзя — только удалить (`onDeleteFailed`).
- **Outbox (`SupportChatOutbox`, `domain/repository`)**: мои сообщения, **не подтверждённые серверным эхом**. `Success` от SDK — не доставка: между обрывом и ping-таймаутом (~20 с) `writeMessage` отвечает успехом и в мёртвый сокет; вне `Ready` — `NotConnected` (сообщение → `Pending`). Запись создаётся до отправки (`enqueue`), после `Success` — `markSent` (обновляет только существующую запись: эхо, пришедшее раньше, её уже удалило), удаляет только эхо или удаление пользователем. При обрыве мои `Sent` без эха → `Pending`; после рестарта `Sent` восстанавливается как `Pending`, а страница истории подтверждает уже дошедшие (сопоставление с границей по времени — старое одноимённое сообщение не подтверждает свежее). Очередь уходит после первичной загрузки истории (at-least-once, дубль возможен только при потерянном эхе). Обновляется **явными переходами**, а не снимком ленты; каждая операция — read-modify-write под мьютексом реализации (`SettingsSupportChatOutbox`, именованное хранилище `AppSettingsFactory.create("supportchat")`, JSON). Очередь переживает смерть VM и процесса; `Pending` уходят после первой страницы истории на `Ready`. Store — `AuthCloseable`: `LogoutUseCase` чистит очередь при смене аккаунта.
- **Локальные копии вложений**: пикер копирует файл в каталог приложения (Android `filesDir/support-chat-attachments`, iOS `Application Support/support-chat-attachments`; Desktop отправляет оригинал без копии). Когда копия не нужна — эхо заменило оптимистичное сообщение, удалён чип композера или неотправленное сообщение — VM вызывает порт `SupportChatAttachmentFiles.discard(path)`; реализация удаляет только файлы своего каталога. Каждая копия лежит в своём подкаталоге `<uuid>/<исходное имя>`: SDK берёт имя файла для сервера из пути, префикс в имени увидела бы поддержка; `discard` удаляет файл вместе с подкаталогом.
- **Платформенные порты** (`presentation/platform`, actual — `composeApp/src/*/filepicker`): `SupportChatFilePicker` (копирование вне main, лимит `SupportChatAttachmentLimits.MAX_BYTES` проверяется до копирования, результат `Picked(file, kind) / Cancelled / TooLarge / Failed`; тип вложения задаёт `SupportChatPickKind` — источник выбора, а не содержимое файла). Контракт — **поток `results`, а не колбэк**: `launchImage()` / `launchDocument()` без параметров, на каждый запуск — один результат, реализация буферизует его (`Channel`) до подписки; `SupportChatEntry` собирает поток в `LaunchedEffect` и передаёт в VM. Причина — на Android процесс могут убить, пока открыт системный пикер (отдельная activity): registry доставит результат уже в новый процесс, колбэк к этому моменту потерян. Android: картинки — Photo Picker (`PickVisualMedia`), документы — SAF (`OpenDocument`); не `GetContent` — часть галерей возвращает выбор в `clipData`, и успешный выбор приходил как `null`. Буфер Android — process-level `object`, не `remember`: результат копирования большого файла не должен уйти в канал композиции, пересозданной вместе с Activity. Photo Picker отдаёт `DISPLAY_NAME` вида `<id>.<ext>` — поведение системы. `SupportChatFileSaver` и `SupportChatAttachmentFiles` — передаются в конструктор VM через `parametersOf` и **не держат Activity-контекст** (VM переживает пересоздание Activity). Имена файлов извне — через `safeFileName` / `uniqueFileName` (`core/common/.../file/FileNames.kt`): basename без `../` и запрещённых символов, существующий файл не перезаписывается.
- **Скачивание и открытие вложений — только по действию пользователя**; при загрузке ленты приходят лишь метаданные (имя, url). Превью картинок Coil грузит сам — это осознанно (решение пользователя). У картинки: тап — встроенный просмотр, кнопка Download (у входящих) — сохранение. У документа (своего и входящего): тап — диалог `SupportChatDocumentActionsDialog` с «Открыть» и «Скачать» («Скачать» — только при наличии url; своё неподтверждённое вложение открывается из локальной копии). Байты качает `repository.downloadFile` через SDK `downloadChatFileUseCase` (лимит 20 МБ проверяет SDK). Открытие — порт `SupportChatFileOpener` (Android: `cacheDir/support-chat-open` + `FileProvider` `${applicationId}.supportchat.files` + `ACTION_VIEW`, нет обработчика → `NoApp`; iOS: QuickLook `UIDocumentInteractionController`, иначе меню «Открыть в…»; Desktop: `java.awt.Desktop.open`). Сохранение — `Загрузки/Pandora Spec` (Android MediaStore с `IS_PENDING`; **API 24–28 — `WRITE_EXTERNAL_STORAGE`** с `maxSdkVersion="28"`, запрашивается в момент сохранения, отказ → `PermissionDenied` и отдельный снекбар; Desktop `~/Downloads`), iOS — экспорт через `UIDocumentPickerViewController` (asCopy), отмена → `Cancelled` без снекбара. Других разрешений не нужно: SAF, Photo Picker, `FileProvider`, MediaStore API 29+ и системные пикеры iOS работают без них. Скачивание и открытие делят один слот (`downloadingAttachmentId`, атомарный захват в `reduce`).
- SDK `isAvailableUseCase` — бизнес-флаг поддержки (часы работы), а НЕ индикатор соединения: не гейть по нему отправку и не возвращай состояние «чат недоступен».
- Ошибки — one-shot `SupportChatEffect` через `postSideEffect` → `sideEffect`/`collectSideEffect`; в state ошибки не хранятся (кроме `history = Error` и флага `isHistoryPagingFailed`).
- UI следует `design/features/support-chat`: адаптивная ширина compact/medium/expanded, wallpaper (`drawWithCache`), skeleton, empty state, tonal bubbles, статусы доставки, Desktop Enter / Shift+Enter. Список — `reverseLayout = true`, newest-first (typing — отдельный item в индексе 0). `LazyColumn` держит позицию по первому видимому ключу, поэтому вставка в индекс 0 уходит под нижний край: после **своей отправки** лента всегда возвращается к последним сообщениям (триггер — счётчик нажатий «Отправить», а не ключ сообщения: серверное эхо через ~20 мс меняет ключ и отменило бы прокрутку); новое **входящее** доводится, только если пользователь был внизу (`firstVisibleItemIndex <= 2`). Анимация мягкая: издалека — мгновенный переход на 6 элементов от низа, затем `animateScrollToItem(0)`. State читается в секциях (баннер, лента, композер), а не в каркасе Body. Триггер пагинации — снапшот условий (`canScrollForward`, `hasMore`, `isLoadingMore`, размер ленты), видимые id — пачкой при смене видимого диапазона; read-отметки VM батчит с debounce ~300 мс. Черновик композера — `rememberSaveable` в экране. Неотправленное сообщение — кнопки «Повторить» / «Удалить» под пузырём (не кликабельный пузырь). `SupportChatActions` — `remember(viewModel)` в entry. Имя файла в чипе композера ограничивается `widthIn(max)`, не `weight` — в элементе `LazyRow` ширина не ограничена, и `weight(fill = false)` схлопывал текст.
- Пузырь обтягивает контент с потолком `maxWidthFraction` (0.82) от колонки чата. Картинка: высота 170dp, ширина по пропорциям (`CmpSubcomposeAsyncImage` + intrinsicSize, ratio 0.75..2, дефолт 4:3). Композер = ширина колонки чата.
- Строки фичи — `supportchat_chat_*` / `supportchat_common_*` (EN/RU, конвенция `{feature}_{screen}_{type}_{name}`, типы из таблицы `docs/localization.md`). Видимый текст — целиком в ресурсах с плейсхолдерами, технические строки — `private const val`. Даты — `rememberCmpDateLabeler()` из `core/ui`. Формат времени пока всегда 24-часовой `HH:mm`.
- После изменений кода запускай `:feature:support-chat:jvmTest`, сборку из `.ai/rules.md` → «Validation» и `./gradlew :composeApp:compileKotlinIosArm64`: платформенные actual компилируются только своими targets.
- Скачивание и открытие вложений — `SupportChatAttachmentTransfers` (presentation): результат — эффект экрана; VM держит один «слот» файловой операции (`downloadingAttachmentId`, захват атомарно в `reduce`).
