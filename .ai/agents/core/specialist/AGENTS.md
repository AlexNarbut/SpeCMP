# core/specialist

- Граница приложения с внешним Specialist SDK (`ru.alarmtrade.common:specialist`): `SpecialistModule` создаёт `SpecialistApp` (конфиг с диспетчерами) и регистрирует SDK-интеракторы как Koin-синглтоны (`authInteractor`, `userInteractor`, `chatInteractor`, `filesInteractor`, `deviceInformationInteractor` и `firmwareFilesInteractor` для прошивки, `serialConnectorInteractor` — COM-порт и др.).
- Composition root подключает модули через `specialistModules(appVersionName, appVersionCode)`: `specialistModule` + `SpecialistAppVersionProvider` с версией от платформы.
- `supportedConnectionTypes()` — транспорты платформы: Android — BLE + USB + `SERIAL` (COM через OTG), desktop — USB + `SERIAL`, iOS — только BLE (COM в SDK — `TODO()`, `serialConnectorInteractor` резолвить только лениво). `SERIAL` в поиске включает только приложение прошивки (`DeviceSelectionNavGraph(serialEnabled = true)`); `serialConnectorInteractor` использует `feature/device/interaction` (`connectSerial`, закрытие сессии).
- Перед созданием `SpecialistApp` модуль передаёт SDK монитор сети: `getOrNull<NetworkMonitor>()` (из `core/network`, кладёт корень приложения) → адаптер → `CommonConfigurator.networkMonitor`. Без него SDK считает сеть всегда доступной и не видит блокировку сети в фоне Android 15. Нет монитора (desktop) — дефолт SDK.
- Сетевые логи SDK выключены во всех сборках (`SpecialistConfig.Network(logLevel = NONE, logWebSocketFrames = false)`): SDK не маскирует тела ответов (переписка) и query (email).
- SDK `ru.alarmtrade.common:specialist` 1.2.4 / `core` 2.0.116 пока тянется из `mavenLocal()` (публикация в `git.pandora.pri` — до мержа).
- `SpecialistInitializer` на старте сохраняет в SDK язык приложения и язык конфигураций (сохранённый, иначе язык приложения). Язык конфигураций меняет настройка приложения через `ConfigurationLanguageStore` (интерфейс в `core/common`, реализация `SpecialistConfigurationLanguageStore`); SDK берёт его в каждый запрос каталога и конфигураций, без него — английский.
- Фичи НЕ обращаются к SDK-интеракторам напрямую — только через профильные API этого модуля.
- `sdk/SdkResponse.kt` — общие хелперы границы с SDK, локальные копии в фичах не заводить:
  - `SpecialistResponse<T>.toResponse()` — ответ SDK в проектный `Response` (без `message` SDK берётся `exception.message`); специфичные ошибки фичи — поверх него (`toResponse().mapIfError { … }`), `Unit`-ответ — `toResponse().map { }`;
  - `(() -> T).resolveOrNull()` — ленивый провайдер интерактора, недоступного на платформе (бросает при резолве) → `null`, отмена пробрасывается;
  - `interactorUnavailable()` — `Response.Error` для неудачного `resolveOrNull()`.
- `sdk/SdkErrorMapper.kt` — внутри `toResponse()` общая ошибка → `AppException(AppError)` из `core/common`, исходная ошибка — в `cause`. Типизированные ошибки SDK распознаются всегда: сеть (`NetworkIsNotAvailableException`, `NetworkNotConnectedError`, `NetworkTimeoutException`, `ContentParsingException` → `ApiError`) и платформа (`Bluetooth*Exception`, `LocationNotEnableForScanException`, `*PermissionException`, `PandoraBleDeviceNotFoundException`/`UsbDeviceNotFoundException`, `InvalidBluetoothSessionState`/`BluetoothGattException` → `PlatformError`); `Throwable.sdkAppError()` — для исключения, пойманного не из `Response`; сырые исключения ktor/платформы (`IOException`, `UnresolvedAddressException`, таймауты ktor, 5xx) — только в `Response.Error.Network`: `IOException` бывает и у USB/serial. Фичи после `toResponse()` проверяют `exception.appError`, а не SDK-типы общих ошибок.
