# Specialist SDK: доработки чата

**Версия SDK:** `ru.alarmtrade.common:specialist` 1.1.76 (Android и iOS).
**Источник:** реализация и эмулятор-проверки `feature/support-chat` в SpeCMP (2026-09…10), разбор байткода
Android-артефактов (`specialist-release.aar`, `specialist-network-release.aar`).
**Для кого:** владельцы SDK. У каждого пункта: проблема → доказательство → предложение → чем обходим сейчас.
**Статус:** реализовано в SDK 1.2.0 / core 2.0.93; SpeCMP мигрирован — `support-chat-sdk-1.2.0-migration.md`.

Приоритет: **P0** — ломает сценарий у пользователя · **P1** — вынуждает клиента писать обходы ·
**P2** — качество / удобство API.

---

## P1-1. SDK владеет единственным соединением чата

Главный пункт плана: остальные проблемы соединения (P0-1, разборы ниже) — следствия того, что сейчас
соединением не владеет никто целиком.

### Как сейчас (1.1.76)

- `openChat` → `WebSocketImpl.connect()`: если сокет уже `Connected` — ничего не делает; иначе открывает
  сокет → `Connected` → `ChatRepositoryImpl` шлёт `subscribe` → сервер отвечает `subscribe_success`.
- `openChat` возвращает `Success` до готовности: ошибка подключения (`KtorWebSocket.connect` → `safeRun`)
  уходит в `state = Error`, а не в результат вызова.
- Обрыв сети (`Ws error` → `clearSession(cause)` → `State.Error`) только публикуется событием —
  переподключения нет.
- Частичное переподключение (`disconnect` → `delay(2000)` → `connect`) есть в двух узких местах: сокет
  закрылся без ошибки при `isOpened == true`; ошибка `subscribe` после подключения. Оно не видно клиенту и
  срабатывает на собственный `close()` (P0-1).
- Состояние доступно только как поток событий без replay (`MutableSharedFlow` без буфера): подписавшийся
  после `openChat` пропускает `Connected` / `SubscribeSuccess`.

Итог: каждое приложение (Android, iOS, desktop) пишет свой автомат подключения, ожидание подписки, цикл
переподключения с backoff, реакцию на фон — и всё это конкурирует с остатками переподключения в SDK.
Сокет при этом общий: его слушают и чат, и удалённый монтаж (`isAvailableRemoteMount`).

### Целевая модель

Одно соединение на процесс, им владеет SDK. Клиент только говорит «мне нужен чат» / «больше не нужен» и
наблюдает состояние.

```kotlin
interface ChatConnection {
    /** Состояние единственного соединения. Всегда актуально, с replay. */
    val state: StateFlow<ChatConnectionState>

    /** События комнаты: сообщения, страницы истории, «печатает», прочтения. */
    val events: SharedFlow<ChatEvent>

    /** Заявка на соединение. Пока есть хотя бы одна активная заявка — SDK держит соединение. */
    fun acquire(): ChatLease

    /** Kotlin-обёртка: заявка живёт, пока собирается поток. */
    fun session(): Flow<ChatConnectionState> // acquire() на старте, release() в finally
}

interface ChatLease {
    fun release() // идемпотентно
}

sealed interface ChatConnectionState {
    data object Idle : ChatConnectionState              // заявок нет, сокет закрыт
    data object Connecting : ChatConnectionState        // первое подключение
    data object Ready : ChatConnectionState             // сокет открыт И получен subscribe_success
    data class Reconnecting(val attempt: Int, val cause: Throwable?) : ChatConnectionState
    data object WaitingForNetwork : ChatConnectionState // сети нет или ОС её блокирует (фон)
    data object AuthFailed : ChatConnectionState        // финал до повторной авторизации
}
```

### Правила поведения

1. **Один сокет, счётчик заявок.** Первая заявка открывает соединение, повторные его не дублируют.
   Последний `release()` закрывает сокет и **отменяет все отложенные переподключения** — после закрытия
   ничего не «воскресает». Опционально — короткий grace period (настраиваемый, по умолчанию 0), чтобы
   переход между экранами не рвал сокет.
2. **`Ready` = подписка комнаты подтверждена.** После каждого переподключения SDK сам заново шлёт
   `subscribe`; каждое попадание в `Ready` — сигнал клиенту перечитать первую страницу истории.
3. **Переподключение, пока есть заявки:** backoff 1 → 2 → 4 → 8 с, дальше максимум (≈30 с) с jitter;
   сброс после `Ready`. Единственный механизм, без параллельных триггеров.
4. **Сеть.** Монитор сети (Android `ConnectivityManager.NetworkCallback`, включая
   `onBlockedStatusChanged` — блокировка в фоне на Android 15+; iOS `NWPathMonitor`): сети нет →
   `WaitingForNetwork` без попыток; сеть вернулась → попытка сразу.
5. **Авторизация.** `Error.Auth` / 401 → `AuthFailed`, попыток нет. После повторного входа при активных
   заявках — подключение заново. Логаут → закрытие соединения и сброс заявок.
6. **Команды при неготовом соединении** (`writeMessage`, `markMessagesAsRead`, …) → сразу
   `Response.Error(NotConnected)`, не «успех в мёртвый сокет» (см. P1-2).
7. **Ошибки — один переход состояния.** Шторм ошибок (iOS, P2-2) не порождает серию событий.
8. **Потокобезопасность.** Открытие, закрытие и переподключение — под одним владельцем (actor / mutex);
   гонки вида P0-1 исключены конструкцией.
9. **Совместимость.** `openChat` / `closeChat` — deprecated-обёртки над `acquire` / `release`.

### Что остаётся клиенту

- Решить, когда чат нужен: держать заявку, покка открыт экран чата (или дольше — политика продукта).
- Показать состояние (плашка «нет соединения», блокировка ввода, `AuthFailed`).
- На каждом `Ready` — запросить первую страницу истории; outbox неотправленных.

**Обход у нас сейчас:** весь этот автомат — в нашем коде: `SpecialistSupportChatRepository.session()`
(подписка на события до `openChat` через `UNDISPATCHED`, ожидание `SubscribeSuccess` 10 с, однократный
финал) и цикл сессий во VM (backoff 1 → 2 → 4 → 8 → 15 с, пауза на `ON_STOP`, немедленная попытка на
`ON_START`).

## P0-1. `closeChat` сам себе запускает переподключение — «воскресший» сокет

Срочный багфикс для линии 1.1.x — до перехода на модель P1-1.

**Проблема — гонка в `close()`.** `SpecialistWsApiImpl.close()` сначала вызывает `disconnect()`
(→ `clearSession()` → `State.Disconnected`) и только **после** этого ставит `isOpened = false`. Наблюдатель
состояния (`SpecialistWsApiImpl$3$1`: `state == Disconnected && isOpened` → `reconnect()`) видит
`Disconnected` при ещё `isOpened == true` и считает собственное закрытие обрывом. Через ~2 с SDK открывает
новый сокет и подписывается на комнату: сокет живёт после ухода из чата без подписчиков.

**Последствия.**
- Лишний сокет после выхода из чата (сеть, батарея, события).
- Следующий `openChat`: `WebSocketImpl.connect()` пропускает подключение при `state == Connected` →
  `subscribe` не уходит → `SubscribeSuccess` не приходит → у нас 10 с «Подключение…» и `OpenFailed`.
- То же после нашего `closeChat` по обрыву в фоне: попытка через 2 с → `UnknownHostException`.

**Доказательство.** Байткод `SpecialistWsApiImpl.close()` (`disconnect` → `isOpened.setValue(false)`),
`SpecialistWsApiImpl$3$1.emit`, `KtorWebSocket.clearSession`. Эмулятор: выход из чата 11:33:36.15 →
`wss` + `subscribe_success` 11:33:38.93; повторный вход → 10 с ожидания. Воспроизводится стабильно.

**Предложение (1.1.x).** В `close()` ставить `isOpened = false` **до** `disconnect()` и отменять
`reconnectJob`. В модели P1-1 закрывается правилами 1 и 8.

**Обход у нас (план, этап 7 `support-chat-session-rework.md`):** `closeChat` перед `openChat` в каждой
сессии — сессия всегда начинается с чистого сокета. «Воскресший» сокет между сессиями снаружи не убрать.

## P1-2. `writeMessage` успешен на мёртвом сокете

**Проблема.** `writeMessageUseCase` возвращает `Success`, даже если сокет уже оборван: отправка — запись в
сокет без подтверждения. Сообщение теряется молча.

**Предложение.** `Response.Error(NotConnected)` при состоянии не `Ready` (правило 6 P1-1); в идеале —
подтверждение доставки (client message id → эхо/ack сервера с серверным id).

**Обход у нас:** outbox «at-least-once»: запись до отправки, `Sent` снимается только по эхо от сервера
(~20 мс), по обрыву неподтверждённые → `Pending` и повтор; сопоставление с историей против дублей.

## P1-3. Пагинация истории: ответ событием без корреляции, нет `hasMore`

**Проблема.**
- `getNextMessagesUseCase` возвращает `Unit`, страница приходит отдельным событием
  `Chat.MessagesPage` в общий поток — нельзя связать ответ с запросом, нельзя понять ошибку запроса.
- В `MessagesPage` нет признака конца истории, хотя сервер его отдаёт (`GetRoomMessages` →
  `content.count`, например 940). Клиент угадывает по `messages.isNotEmpty()` → лишний пустой запрос.
- Номер страницы — внутреннее состояние SDK (`lastDownloadedPage`), сбрасывается только через
  `openChat(resetPages = true)`.

**Предложение.** `suspend fun loadMessages(page: Int / cursor): Response<MessagesPage>` с
`hasMore`/`total`; курсор (id последнего сообщения) вместо номера страницы — новые сообщения не сдвигают
страницы. Запрос истории — HTTP, от состояния сокета не зависит.

**Обход у нас:** `HistoryPage` из события, таймаут 15 с и номер запроса во VM, дедупликация по id при
слиянии.

## P1-4. `prepareUrl` ломает URL файлов с query

**Проблема.** URL вложений с `?` кодируется в `%3F` → сервер отвечает 404 с пустым телом; старые файлы
чата не скачиваются через SDK.

**Предложение.** Не перекодировать готовый URL (или кодировать только path-сегменты); отдать
`downloadFile(url): Response<ByteArray|Path>` с лимитом размера.

**Обход у нас:** скачивание мимо SDK — `FileDownloader` (Ktor) в `core/network`, лимит 20 МБ.

## P2-1. Безопасность логирования

**Проблема.** Ktor-логгер SDK пишет в logcat полный заголовок `authorization: Bearer …` и тела ответов
(в том числе переписку чата); `WebSocket send/receive2` — содержимое сообщений.

**Предложение.** Санитизация `Authorization`/токенов, уровень логирования настраивается клиентом,
по умолчанию в release — выключено.

## P2-2. iOS: шторм ошибок при обрыве

**Проблема.** При обрыве на iOS поток событий выдаёт `Response.Error` с очень высокой частотой (~кГц)
вместо одного события.

**Предложение.** Одно событие обрыва на соединение; в модели P1-1 — один переход состояния (правило 7).

**Обход у нас:** финал сессии фиксируется один раз (`CompletableDeferred`), остальное игнорируется.

## P2-3. Потоки SDK бросают исключения мимо `Response`

**Проблема.** `getChatEventsFlowUseCase` может завершиться исключением вместо `Response.Error` —
контракт `Response` нарушается.

**Предложение.** Все публичные `Flow` — без исключений, ошибки как элементы `Response.Error` /
состояние соединения.

**Обход у нас:** `safeFlowRun` вокруг потока событий.

## Открытые вопросы к SDK

1. Кто внутри SDK ещё пользуется сокетом чата (удалённый монтаж — `isAvailableRemoteMount`, счётчик
   непрочитанных)? В модели P1-1 каждый такой сценарий берёт свою заявку.
2. Нужен ли grace period при `release()` и какой (по умолчанию 0)?
3. Есть ли у сервера ack на `write message` с клиентским id?
4. Поддерживает ли `GetRoomMessages` курсор (до id) вместо `pageNumber`?
