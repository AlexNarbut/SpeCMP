## Цель и границы

Перестроить **ядро** фичи — модель соединения, ленту сообщений, outbox, загрузку истории,
отправку и ретраи — так, чтобы все высокие и средние пункты review-2 закрывались
конструкцией, а не точечными guard'ами. UI, строковые ресурсы, дизайн и уже работающие
решения (`reverseLayout`, `CmpAsyncImage`, `rememberCmpDateLabeler`, per-entry VM,
`AuthCloseable`, контракт истории с таймаутом) **сохраняются** и правятся точечно.

В объёме: `feature/support-chat`, платформенные actual в `composeApp/src/*/filepicker`,
`core/ui` (effects), `core/*` (Settings), документация (`.ai/*` → `.ai/generate.sh`).

Вне объёма: изменения Specialist SDK; новые продуктовые функции (typing с нашей стороны,
редактирование сообщений); миграция `core/localization` на общий Settings (см. открытые вопросы).

## Отклонения от плана и решения по ходу реализации

- **Outbox API:** `enqueue` (upsert, в т.ч. переход в `Failed`) + `remove` вместо
  `markSent`/`markFailed` — того же достаточно, меньше методов.
- **Timeline:** вместо `tryStartRetry` — общий `tryTransition(id, from, to)` (ретрай `Failed → Sending`
  и очередь `Pending → Sending`); добавлен `withRead`.
- **Пагинация:** гейтинг не по `isInitialHistoryLoaded`, а мьютексом со skip — `onLoadMore` до
  первичной загрузки просто повторяет первичную. Добавлен флаг `isHistoryPagingFailed`: без него
  новый триггер пагинации крутил бы цикл «ошибка → тост → повтор».
- **Локальные копии вложений:** новый порт `SupportChatAttachmentFiles.discard(path)` (actual в
  `composeApp`, передаётся в VM через `parametersOf`). VM удаляет копию, когда эхо заменило
  сообщение, удалён чип или неотправленное сообщение. `release()` outbox при логауте чистит только
  записи: порт — UI-уровня, в data-слое его нет; оставшиеся копии — в каталоге приложения, не в «Загрузках».
- **Пикер:** результат дополнен `TooLarge` / `Failed` (+ эффект `AttachmentRejected`, строки EN/RU),
  лимит `SupportChatAttachmentLimits.MAX_BYTES` = 20 МБ. На Android колбэк ожидающего выбора —
  в объекте процесса, а не `rememberSaveable` (лямбду не сохранить); переживает пересоздание
  Activity, не переживает смерть процесса. iOS: копии в `Application Support`, документ копируется
  на фоновой очереди.
- **Failed-сообщение:** явные кнопки «Повторить» / «Удалить» под пузырём вместо long-press/меню —
  доступнее и без конфликта с тапом по картинке; a11y-строки не нужны (у кнопок видимый текст),
  `supportchat_chat_a11y_retry` удалён как осиротевший.
- **U-7:** формат времени оставлен 24-часовым `HH:mm` (считается из `Instant` в поясе устройства):
  12-часовой формат для EN требует решения, как держать AM/PM в ресурсах. Чипы empty state
  оставлены — они из дизайн-макета.
- **U-8:** ключи приведены к существующим типам таблицы: `hint_*` (чипы), `msg_typing_author`,
  `title_offline`/`subtitle_offline`/`title_connecting`, `msg_download_success`/`error_download`,
  `a11y_status_*`, `label_size_*`; в `composeApp` — `composeapp_picker_*`. Таблицу не расширяли.
- **A-1:** SDK 1.1.76 не отдаёт размер/mime документа — проверка размера до загрузки невозможна;
  комментарий об OOM исправлен, пустой ответ → ошибка в репозитории.
- **Settings:** `AppSettingsFactory` изолирует ключи префиксом `"<name>."` поверх одного no-arg
  `Settings` (именованных платформенных хранилищ no-arg без Android-контекста не даёт). Ключ outbox
  сменился (`support_chat_outbox` → `supportchat.outbox`): очередь из предыдущей сборки ветки не
  переносится — фича не выпущена.
- **iOS:** в `rememberSupportChatFileSaver.kt:113` осталось предупреждение `BetaInteropApi`
  (`NSData.create`) — существовало до задачи.

## Этап 9 — дефекты, найденные на Android-эмуляторе (2026-09-29)

Прогон: эмулятор `sdk_gphone64_arm64` (Android 16), debug-сборка, реальный сервер.

| # | Что наблюдается | Причина (подтверждена логами) |
|---|---|---|
| E-1 | Выбор документа/картинки в системном пикере не прикрепляет файл — чипа нет, ошибки нет | `AppActivity` — `launchMode="singleInstance"`: пикер стартует в отдельной задаче (`NEW_TASK`), результат приходит `RESULT_CANCELED` (`resultCode=0 data=null`). Было в манифесте до переработки |
| E-2 | Пока открыт пикер, Android рвёт TCP-сокеты фонового приложения → по возвращении баннер «Нет соединения» при живом интернете | `InetDiagMessage: Destroyed live tcp sockets for uids={10226}` → `Ws error: Software caused connection abort`; автоматических реконнектов нет — нужен ручной «Повторить» |
| E-3 | Без сети «Повторить» снимает баннер, хотя сокет не подключился; баннер больше не возвращается | Гонка в `connect()`: ошибка WS-события приходит **во время** `openChat()` (`switching to offline`), затем `openChat()` возвращает `Success` и безусловно ставит `Online` |
| E-4 | После E-3 сообщение, отправленное без сети, получает «отправлено» и **теряется** (на сервере его нет, в outbox нет) | SDK `writeMessage` отвечает `Success` при мёртвом сокете; `Sent` сразу удаляет запись из outbox |

**План исправлений:**

- [x] E-1: `androidApp/AndroidManifest.xml` — `launchMode="singleInstance"` → `"singleTask"`
      (один экземпляр сохраняется, результаты activity-for-result возвращаются). Проверить пикер
      документа и картинки на эмуляторе.
- [x] E-3: `connect()` — после `openChat()` ставить `Online` только если состояние всё ещё
      `Connecting` (ошибка события во время открытия побеждает). Тест: ошибка события во время
      `openChat` → остаётся `Offline`.
- [x] E-4: `Sent` от SDK — не подтверждение доставки. Запись outbox живёт до серверного эха
      (замена оптимистичного сообщения), а при переходе в `Offline` мои `Sent`-без-эха
      возвращаются в `Pending` и уходят повторно после переподключения. Риск — дубль, если эхо
      потерялось, а сообщение дошло (at-least-once). Тест: `Sent` без эха → обрыв → `Pending` →
      реконнект → повторная отправка.
- [x] Проверено на эмуляторе: документ и картинка прикрепляются и уходят онлайн (эхо приходит,
      локальная копия удаляется); без сети вложения и ввод заблокированы, баннер после
      «Повторить» остаётся. E-4 закрыт тестами (обрыв посреди отправки вручную не воспроизвести).
      Реализация E-4: запись outbox создаётся до отправки, `markSent` только обновляет
      существующую запись, эхо удаляет; при обрыве `Sent` без эха → `Pending`; после рестарта
      `Sent` → `Pending`, а страница истории подтверждает уже дошедшие (с границей по времени —
      старое одноимённое сообщение не «съедает» свежее). Очередь отправляется после первичной истории.

## Этап 10 — E-2 и новые дефекты с эмулятора (одобрено 2026-09-29, реализовано)

**E-2, исследование (ответ на вопрос «почему рвёт»):**
- Это политика Android 15+: `dumpsys netpolicy` → `blocked=APP_BACKGROUND`. Процесс, у которого
  не осталось видимой Activity, через ~5 с теряет сеть, а его сокеты уничтожаются
  (`InetDiagMessage: Destroyed live tcp sockets`). Файловый пикер (DocumentsUI) полноэкранный —
  наша Activity уходит в `onStop`; Photo Picker — нижняя шторка, Activity остаётся видимой, сокет
  живёт (проверено: 10 с в пикере без обрыва). Удержать сокет в фоне можно только
  foreground-сервисом — для чата не предлагаю.
- В SDK автореконнект **есть**, но узкий: `SpecialistWsApiImpl` слушает состояние сокета и при
  `Disconnected` (если сессия открыта) вызывает `reconnect()` = disconnect → 2 с → connect.
  На `Error` (Android `onFailure`: «Software caused connection abort») реконнекта нет, а наш
  `goOffline()` вызывает `closeChat()` — это снимает `isOpened` и выключает и тот реконнект.

**E-2, план:**
- [x] Автопереподключение в VM, пока экран виден: при `Offline` — попытки `openChat()` с
      backoff 1 → 2 → 4 → 8 → 15 с (дальше каждые 15 с), до `Online`. Одна попытка за раз;

## Этап 14 — состояние соединения в событиях + сессия в репозитории (одобрено 2026-09-30)

**Зачем.** Сейчас VM собирает состояние соединения из разрозненных сигналов: `ConnectionChanged(Boolean)`,
`Response.Error` в потоке событий, результат `openChat()` (который отвечает `Success`, даже если сокет
не поднялся). Отсюда гонка E-3, хак «`Online`, только если всё ещё `Connecting`», поколения сессии
`SupportChatSessionId`, ручные `startEventCollection` / `closeChat` в VM и `appScope` в `onCleared`.

**Сигналы SDK 1.1.76** (проверено по классам): `ChatEvent.Connection.Connected` / `Disconnected` —
сокет; `ChatEvent.ChatRoom.SubscribeSuccess` — комната подписана (в логах `subscribe_success`),
настоящее «можно отправлять»; `ChatEvent.Error.Auth` — ошибка авторизации (сейчас игнорируется);
`Response.Error` в потоке — обрыв (Android/iOS `onFailure`, на iOS потоком ~кГц).

**Domain:**
- [ ] `SupportChatConnectionState`: `Connecting` (профиль → `setChatType` → `openChat` → сокет),
      `Connected` (пришёл `SubscribeSuccess`), `Disconnected(reason)`, где
      `reason = OpenFailed | Lost | AuthFailed`.
- [ ] `SupportChatEvent`: `ConnectionChanged(Boolean)` → `Connection(state)`; остальные события без изменений.
- [ ] Контракт `fun session(): Flow<SupportChatEvent>` вместо `observeEvents()` + `openChat()` +
      `closeChat(session)`. Одна подписка = одна сессия: подписка открывает чат, отмена или
      завершение закрывает. `SupportChatSessionId` удаляется.

**Data (`SpecialistSupportChatRepository.session()`):**
- [ ] `channelFlow`: `Connection(Connecting)` → подписка на события SDK **до** `openChat()` (порядок
      гарантирован внутри потока, без `yield()` в VM) → `openChat()`; ошибка → `Disconnected(OpenFailed)`,
      поток завершается.
- [ ] Нормализация внутри: `Connected` — только по `SubscribeSuccess`; `Connection.Disconnected` или
      `Response.Error` → один `Disconnected(Lost)` (шторм ошибок iOS схлопывается), поток
      завершается; `Error.Auth` → `Disconnected(AuthFailed)`. Состояние эмитится только при изменении.
- [ ] Нет `SubscribeSuccess` за 10 с после `openChat` → `Disconnected(OpenFailed)` (страховка от
      вечного `Connecting`).
- [ ] Закрытие — в `finally` под `withContext(NonCancellable)` + `connectionMutex`; `release()` при
      логауте закрывает активную сессию, если она есть.
- [ ] `loadNextMessages` / отправка — только при активной сессии (KDoc контракта).

**Presentation (VM):**
- [ ] Цикл сессии: собрать `session()` → поток завершился → backoff (1 → 2 → 4 → 8 → 15 с, сброс
      после `Connected`) → собрать снова. `connection` в UI выводится из `Connection(state)`:
      `Connected` → `Online`, `Disconnected` → `Offline` (+ `hasConnectionIssue`), `Connecting` — как сейчас.
- [ ] Первичная история и отправка очереди — по `Connected`, а не по результату `openChat`.
- [ ] Удаляется из VM: хак E-3, `startEventCollection`, `goOffline → closeChat`, `session`/поколения,
      `appScope` и закрытие в `onCleared` (отмена `viewModelScope` сама закрывает сессию через
      `NonCancellable`), `yield()` в `init`. Сохраняется: `requeueUnconfirmed` при `Disconnected`,
      пауза попыток на `ON_STOP`.
- [ ] `AuthFailed` — стоп цикла сессий, плашка без спиннера (решение 2).

**Тесты / проверка:**
- [ ] Фейк репозитория с управляемым `session()`-потоком; переписать тесты соединения. Новые:
      `Connected` только по подписке комнаты, шторм ошибок → один `Disconnected`, нет
      `SubscribeSuccess` → таймаут, отмена сбора закрывает сессию, `AuthFailed`.
- [ ] Эмулятор: обрыв/возврат сети, пикер > 5 с, выход из чата закрывает сокет, логаут.

**Решения пользователя (2026-09-30):**
1. `ON_STOP`: сокет держим, только пауза попыток; сессия закрывается при уходе с экрана чата.
2. `AuthFailed`: автопереподключение останавливается, плашка «Не удалось авторизоваться в чате»;
   новая попытка — при повторном входе в чат. Логаут не делаем.

### Этап 14 — корректировка по замечанию пользователя (2026-09-30) — **ждёт апрува**

Первая реализация репозитория переусложнена (поколения сессии, `@Volatile`, сброс пагинации внутри
репозитория). Репозиторий пишется заново, тонким:

- [ ] **Одна сессия.** `sessionGeneration`/проверки «чужой» сессии убираются: сессия в приложении одна,
      полную очистку при смене пользователя гарантирует `release()` (`LogoutUseCase`). Поля:
      `mutex` (сериализует открытие/закрытие), `myEmail` (identity текущей сессии, обычное поле —
      пишется при открытии до `openChat`), ожидающий ответ страницы истории.
- [ ] `session()` — `channelFlow`: `Connecting` → подписка на события SDK → профиль + `setChatType` +
      `openChat` → `Connected` по `SubscribeSuccess` (таймаут 10 с → `Disconnected(OpenFailed)`) →
      события → `Disconnected(Lost | AuthFailed)` один раз → закрытие в `finally` под `NonCancellable`.
- [ ] **Сброс пагинации — во VM.** Контракт: `loadNextMessages(resetPages: Boolean = false)`; репозиторий
      только выполняет (`openChat(resetPages = true)` перед запросом страницы). VM держит флаг «после
      таймаута страницы следующий запрос — со сбросом», снимает его после успешной страницы и при
      новой сессии.
- [ ] `release()` = закрыть текущую сессию.
- [ ] Остальное (`send*`, `markMessagesAsRead`, `downloadFile` через `FileDownloader`, маппинг) — без изменений
      по поведению. VM и тесты — как в плане Этапа 14, плюс флаг сброса пагинации во VM.
- Принятый риск (решение пользователя): при очень быстром повторном входе закрытие старой сессии
  может закрыть новую — новая подписка это увидит как `Disconnected(Lost)` и переподключится.
