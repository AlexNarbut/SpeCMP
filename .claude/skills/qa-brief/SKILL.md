# Бриф для QA

Готовишь для живого тестировщика одну HTML-страницу: что есть в приложении (или что поменялось) и как это
проверить. Читатель — **не разработчик** и, возможно, впервые видит приложение: никаких имён классов,
модулей, тегов и терминов SDK; названия — как на экране, по-русски.

Все пути — от корня репозитория. Файлы скилла: `.agents/skills/qa-brief/` — `sections.md` (карта разделов),
`templates/brief.example.json` (формат данных), `templates/brief.html` (страница), `scripts/changes.sh`
(изменения по git), `scripts/render.sh` (сборка страницы). Результат: `.ai-qa/briefs/<slug>/`
(`brief.json` + `index.html`, не в git), `slug`:

| Режим | slug | Охват |
|---|---|---|
| `qa-brief full` | `full-<ГГГГ-ММ-ДД>` | все разделы из `sections.md` полностью |
| `qa-brief branch <ветка> [база=develop]` | `branch-<ветка без />-<ГГГГ-ММ-ДД>` | коммиты `база...ветка` |
| `qa-brief since <от> [до] [ветка=develop]` | `develop-<от>-<до>` | коммиты ветки за период (до — по умолчанию сегодня) |

Без аргументов — спроси режим (варианты: всё приложение / ветка / период).

## 1. Изменения

`.agents/skills/qa-brief/scripts/changes.sh <режим> …` (те же аргументы, что у скилла) — печатает шапку
(ветка, коммит, версия сборки, период, число коммитов) и коммиты с файлами, разложенные по разделам
`sections.md`. В `full` — только шапка и даты последних изменений по разделам.

Скрипт упал (нет ветки, пустой период) — покажи ошибку и спроси, что исправить. Пустой охват (нет
коммитов в разделах приложения) — скажи об этом и не делай пустую страницу.

## 2. Что проверять по разделам

Для каждого раздела в охвате (в `full` — для всех):

1. Прочитай источники раздела из `sections.md`: `AGENTS.md` модулей, строки экранов (`composeResources/values-ru/strings.xml` —
   отсюда названия кнопок и сообщений), при необходимости макеты `design/features/…` и заметки `.claude/tasks/…`.
2. В режимах `branch` / `since` — прочитай сами коммиты раздела (`git show --stat <hash>`, при неясности — дифф),
   чтобы понять поведение **для пользователя**: что появилось, что поменялось, что исправлено.
3. Составь кейсы: короткое название, шаги (действия на экране), ожидаемый результат, приоритет, платформы.
   - `full`: основной сценарий раздела целиком + ошибки и пограничные случаи из `sections.md` («Всегда проверять»).
   - `branch` / `since`: кейсы на каждое изменение (отметка `new: true`) + короткая регрессия соседнего
     сценария; исправленный баг — кейс «воспроизвести старые шаги → бага нет».
   - Кейс проверяет одно поведение; 3–8 шагов; ожидаемое — наблюдаемое на экране, без «работает корректно».
   - Приоритет: `high` — основной путь и то, что ломает работу с блоком (запись настроек, прошивка);
     `normal` — остальное; `low` — косметика.
   - Платформы — только где сценарий реально есть (BLE — телефон, USB — Android/desktop; см. `sections.md`).
4. «Известные ограничения» раздела — то, что **не нужно** заводить багом (из `AGENTS.md`: «не подключено»,
   «не проверено на железе», ограничения SDK). Формулируй для тестировщика.

Разделов много (`full`) — можно раздать разделы субагентам общего назначения (по 2–3 раздела, до 4
параллельно): каждому — пути источников, формат кейса из `templates/brief.example.json` и правила выше;
ответ — JSON-массив `sections`. Сводишь и вычитываешь сам: единый тон, нет кода и внутренних имён.

## 3. Данные и страница

Заполни `.ai-qa/briefs/<slug>/brief.json` по `templates/brief.example.json`:

- `title` — название теста («Полная проверка приложения», «Ветка feature/vehicle-select», «Изменения develop
  01.09–27.10»); `summary` — 2–4 предложения: что это за приложение / что в этом выпуске и на что обратить
  внимание в первую очередь.
- `meta` — из шапки `changes.sh`: версия, ветка, коммит, период изменений, дата брифа.
- `general` — блоки «Перед началом» (сборки и платформы, тестовый аккаунт — **без паролей**, где взять блок,
  какие нужны: BLE-блок, USB-кабель, интернет), «Как сообщать о баге» (платформа, версия, шаги, ожидалось /
  получилось, видео или скриншот, время — по нему ищут логи).
- `sections` — в порядке `sections.md`; в `branch` / `since` — только затронутые, плюс короткая регрессия
  авторизации и подключения, если менялся общий код (`core`, `composeApp`, платформы).
- `id` брифа — slug: по нему страница хранит отметки тестировщика.

Собери страницу: `.agents/skills/qa-brief/scripts/render.sh .ai-qa/briefs/<slug>` → `index.html` (один файл
без внешних зависимостей: отметки «OK / Баг / Блокер / Пропуск», комментарии, фильтр по платформе, прогресс,
кнопка «Скопировать отчёт»). Скрипт проверяет JSON и обязательные поля — ошибки исправь и запусти снова.

## 4. Сдача

Покажи пользователю: путь к `index.html`, число разделов и кейсов (из них `high` и новых). Если доступна
публикация страниц (например, инструмент Artifact) — предложи опубликовать `index.html`, чтобы отправить
тестировщику ссылку; иначе — файл можно переслать как есть.

## Правила

- Только факты из кода, документации и коммитов; не знаешь, как ведёт себя экран, — не выдумывай шаги:
  открой строки/экран или пометь кейс «уточнить у разработчика» в `note`.
- Без паролей, токенов и личных данных в брифе.
- Код приложения не меняешь.
