# Бриф для QA

Готовишь для живого тестировщика одну HTML-страницу: что есть в приложении (или что поменялось) и как это
проверить. Читатель — **не разработчик** и, возможно, впервые видит приложение: никаких имён классов,
модулей, тегов и терминов SDK; названия — как на экране, по-русски.

Все пути — от корня репозитория. Файлы скилла: `.agents/skills/qa-brief/` — `sections.md` (карта разделов),
`templates/brief.example.json` (формат данных), `templates/brief.html` (страница), `scripts/changes.sh`
(изменения по git), `scripts/render.sh` (сборка страницы). Результат: `.ai-qa/briefs/<slug>/`
(`brief.json` + `index.html`, не в git), `slug`:

| Режим | slug | Охват |
|---|---|---|
| `qa-brief full` | `full-<ГГГГ-ММ-ДД>` | все разделы из `sections.md` полностью |
| `qa-brief section <id> [<id>…]` | `section-<id>[-<id>…]-<ГГГГ-ММ-ДД>` | перечисленные разделы полностью (как в `full`) |
| `qa-brief branch <ветка> [база=develop]` | `branch-<ветка без />-<ГГГГ-ММ-ДД>` | коммиты `база...ветка` |
| `qa-brief since <от> [до] [ветка=develop]` | `develop-<от>-<до>` | коммиты ветки за период (до — по умолчанию сегодня) |

Без аргументов — спроси режим (варианты: всё приложение / разделы / ветка / период). Несколько разделов, на
каждый нужен **свой** бриф (`section firmware`, `section clone` …) — это отдельные запуски, по брифу на раздел.

## 1. Изменения

`.agents/skills/qa-brief/scripts/changes.sh <режим> …` (те же аргументы, что у скилла) — печатает шапку
(ветка, коммит, версия сборки, период, число коммитов) и коммиты с файлами, разложенные по разделам
по строкам «Пути» из `sections.md` (таблицы в скрипте нет — новый модуль добавляй только в `sections.md`).
В `full` — только шапка и даты последних изменений по разделам; в `section` — шапка и последние коммиты
выбранных разделов (неизвестный `id` — ошибка со списком разделов).

В «Прочем» (`other`) оказался код приложения (модуль `feature/*`, `core/*` вне `platform` и т.п.) — значит,
у раздела не хватает пути: допиши его в `sections.md` и перезапусти, а не раскладывай вручную.

Скрипт упал (нет ветки, пустой период) — покажи ошибку и спроси, что исправить. Пустой охват (нет
коммитов в разделах приложения) — скажи об этом и не делай пустую страницу.

## 2. Что проверять по разделам

Для каждого раздела в охвате (в `full` — для всех, в `section` — для перечисленных):

1. Прочитай источники раздела из `sections.md`: `AGENTS.md` модулей, строки экранов
   (`core/localization/src/commonMain/composeResources/values-ru/<префикс>.xml` — отсюда названия кнопок и
   сообщений), при необходимости макеты `design/features/…` и заметки `.claude/tasks/…`. Раздел со «Связано» —
   учти, что его изменения могут затрагивать и связанные разделы.
2. В режимах `branch` / `since` — прочитай сами коммиты раздела (`git show --stat <hash>`, при неясности — дифф),
   чтобы понять поведение **для пользователя**: что появилось, что поменялось, что исправлено.
3. Составь кейсы: короткое название, пары «шаг → ожидаемый результат» (`checks`), приоритет, платформы.
   - `full` / `section`: основной сценарий раздела целиком + ошибки и пограничные случаи из `sections.md` («Всегда проверять»).
   - `branch` / `since`: кейсы на каждое изменение (отметка `new: true`) + короткая регрессия соседнего
     сценария; исправленный баг — кейс «воспроизвести старые шаги → бага нет».
   - Кейс проверяет одно поведение; 1–8 шагов (общая подготовка — в `preconditions` секции, не в каждом кейсе).
   - Формат — «Шаг-N → ОР-N»: у **каждого** шага свой ожидаемый результат (`checks: [{step, expected}]`), а не
     два отдельных списка. Шаг — одно действие (или короткая связка, после которой есть что проверить); ОР —
     наблюдаемое на экране после этого шага, без «работает корректно» (дословный текст экрана — можно).
   - **Порядок кейсов в разделе: сначала ошибки и отказы, потом основной путь.** Тестировщик прогоняет кейсы
     подряд: ошибки ввода и отказы сервера (неверный пароль, занятый email, ошибки полей, нет сети) идут до
     успешного сценария, который меняет состояние (регистрация, вход, сохранение). Пример авторизации: ошибки
     полей регистрации → регистрация на занятый email → регистрация → вход в неактивированный аккаунт →
     ошибка восстановления пароля → восстановление пароля. В конфигураторе «нет интернета при выборе модели» и
     «недавние модели» — до создания конфигурации.
   - Кейс, который нельзя пройти без особых данных (автомобиль с нужными значками, большой файл, блок с
     заводскими CAN-настройками), — с конкретикой в `note`: где взять данные или «данные выдаёт разработчик»;
     без этого кейс не заводи.
   - Приоритет: `high` — основной путь и то, что ломает работу с блоком (запись настроек, прошивка);
     `normal` — остальное; `low` — косметика.
   - Платформы — только где сценарий реально есть (BLE — телефон, USB — Android/desktop; см. `sections.md`).
4. «Известные ограничения» раздела — то, что **не нужно** заводить багом (из `AGENTS.md`: «не подключено»,
   «не проверено на железе», ограничения SDK). Формулируй для тестировщика.

Разделов много (`full`) — можно раздать разделы субагентам общего назначения (по 2–3 раздела, до 4
параллельно): каждому — пути источников, формат кейса из `templates/brief.example.json` и правила выше;
ответ — JSON-массив `sections`. Сводишь и вычитываешь сам: единый тон, нет кода и внутренних имён.

## 3. Данные и страница

Заполни `.ai-qa/briefs/<slug>/brief.json` по `templates/brief.example.json` (кейсы — в формате `checks`;
старые брифы со списками `steps`/`expected` страница тоже показывает):

- `title` — название теста («Полная проверка приложения», «Прошивки — полная проверка», «Ветка feature/vehicle-select», «Изменения develop
  01.09–27.10»); `summary` — 2–4 предложения: что это за приложение / что в этом выпуске и на что обратить
  внимание в первую очередь.
- `meta` — из шапки `changes.sh`: версия, ветка, коммит, период изменений, дата брифа.
- `general` — блоки «Перед началом» (сборки и платформы, тестовый аккаунт — **без паролей**, где взять блок,
  какие нужны: BLE-блок, USB-кабель, интернет), «Как сообщать о баге» (платформа, версия, шаги, ожидалось /
  получилось, видео или скриншот, время — по нему ищут логи).
- `sections` — в порядке `sections.md`; в `branch` / `since` — только затронутые, плюс короткая регрессия
  авторизации и подключения, если менялся общий код (`core`, `composeApp`, платформы).
- `id` брифа — slug: по нему страница хранит отметки тестировщика.

Собери страницу: `.agents/skills/qa-brief/scripts/render.sh .ai-qa/briefs/<slug>` → `index.html` (один файл
без внешних зависимостей: отметки «OK / Баг / Блокер / Пропуск», «Комментарий тестировщика» у каждого кейса,
«✎ Исправить кейс» — тестировщик правит название, шаги и ожидаемое, если в описании ошибка (исходный вариант
виден рядом, «Вернуть исходный»), фильтр по платформе, прогресс, «Скопировать / Скачать отчёт»). Отметки,
комментарии и правки хранятся в браузере тестировщика (по `id` брифа). Скрипт проверяет JSON и обязательные
поля — ошибки исправь и запусти снова.

## 4. Сдача

Покажи пользователю: путь к `index.html`, число разделов и кейсов (из них `high` и новых). Если доступна
публикация страниц (например, инструмент Artifact) — предложи опубликовать `index.html`, чтобы отправить
тестировщику ссылку; иначе — файл можно переслать как есть.

## Отчёт тестировщика

Пользователь принёс отчёт со страницы (markdown): в «Проблемы» — баги и блокеры с комментариями; в
«Исправленные кейсы» — правки описаний «было → стало». Замечания к порядку кейсов и формулировкам («должен идти
раньше», «переписать», «не нашёл такой экран») — тоже правки брифа: переставь, перепиши по коду и, если это
правило, а не частный случай, допиши его в этот файл или в «Всегда проверять» `sections.md`. Правки перенеси в `brief.json` того же брифа и пересобери
страницу; если правка показывает, что неверно знание о разделе (не тот экран, не та кнопка, нет такого
сценария), — поправь и «Всегда проверять» в `sections.md`, чтобы ошибка не повторилась в следующих брифах.

## Правила

- Только факты из кода, документации и коммитов; не знаешь, как ведёт себя экран, — не выдумывай шаги:
  открой строки/экран или пометь кейс «уточнить у разработчика» в `note`.
- Без паролей, токенов и личных данных в брифе.
- Код приложения не меняешь.
